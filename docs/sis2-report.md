# SIS2 / T7: отчёт по REST и gRPC

Сервис счётчиков лайков и просмотров с общей бизнес-логикой и двумя транспортами: REST/JSON и gRPC/Protobuf. Хранилища: PostgreSQL (лайки, счётчики, журнал batch) и Redis (дедупликация и накопление просмотров). Язык: Go (согласован пользователем; в программе курса указан Java, разрешение преподавателя на Go нужно получить отдельно).

## 1. Почему gRPC

В SIS1 описан только REST. gRPC добавлен по требованию SIS2 как транспорт для сравнения. Ожидаемые плюсы для этой задачи:

- строгий контракт `.proto`, генерация клиента и сервера;
- компактное бинарное тело сообщения, особенно для пачек просмотров (50 событий);
- одно HTTP/2-соединение с мультиплексированием для клиентов с высоким параллелизмом.

Минусы: сложнее отладка (нет curl «из коробки»), браузер не вызывает gRPC напрямую, нужен кодогенератор. Поэтому REST остаётся для веб-клиента, gRPC подходит для сервис-сервисных вызовов.

## 2. Методика

Клиент `cmd/bench`, оркестрация `benchmarks/run.py`. Одинаковые данные, операции и параллелизм для обоих протоколов; соединения переиспользуются; ретраев нет; без TLS и сжатия; REST — HTTP/1.1, gRPC — HTTP/2. Отдельное Docker-окружение (API 2 CPU, PostgreSQL 2 CPU и 1 ГБ, Redis 1 CPU, tmpfs). Перед каждым запуском состояние сбрасывается (100 постов, пустой Redis). Порядок протоколов чередуется. Latency включает все попытки, ошибки не исключаются. Всё запущено на одном ноутбуке, фоновая нагрузка хоста не исключена, поэтому абсолютные цифры ориентировочные.

Операции: `read` (20 постов), `views` (пачка 50, новые viewer_id), `likes` (like/unlike по 100 постам), `duplicates` (повтор тех же просмотров), `hot` (все лайки на один пост), `freshness` (время до видимости принятого просмотра).

## 3. Результаты

### 3.1 Чтение, 20 постов (полный профиль: прогрев 10 с, замер 60 с, 3 прогона, среднее)

| Параллелизм | Протокол | RPS | p50, мс | p95, мс | p99, мс | Ошибки |
|---|---|---|---|---|---|---|
| 1 | REST | 2706 | 0.36 | 0.46 | 0.54 | 0 |
| 1 | gRPC | 2939 | 0.33 | 0.43 | 0.50 | 0 |
| 10 | REST | 9169 | 0.52 | 0.93 | 43.6 | 0 |
| 10 | gRPC | 8700 | 0.58 | 1.15 | 38.3 | 0 |
| 50 | REST | 6395 | 3.62 | 56.2 | 66.9 | 0 |
| 50 | gRPC | 5669 | 2.11 | 74.7 | 80.1 | 0 |

При параллелизме 50 хвосты (p95/p99 в десятки мс) и падение RPS относительно c=10 говорят, что окружение упирается в ресурсы (CPU API/PostgreSQL на общем ноутбуке), а не в протокол.

### 3.2 Остальные операции (короткий профиль: прогрев 2 с, замер 8 с, 1 прогон, параллелизм 10)

Профиль сокращён относительно ТЗ (10 с / 60 с / 3 прогона), поэтому разброс не оценён и числа менее надёжны.

| Операция | Протокол | RPS | p50, мс | p95, мс | p99, мс | Ошибки |
|---|---|---|---|---|---|---|
| views (50 в пачке) | REST | 3036 | 2.12 | 4.87 | 49.6 | 0 |
| views | gRPC | 3466 | 1.89 | 4.10 | 51.0 | 0 |
| likes | REST | 7208 | 0.71 | 1.27 | 46.9 | 0 |
| likes | gRPC | 6643 | 0.75 | 1.31 | 49.5 | 0 |
| duplicates | REST | 12026 | 0.78 | 1.32 | 1.65 | 0 |
| duplicates | gRPC | 16590 | 0.55 | 0.95 | 1.30 | 0 |
| hot (один пост) | REST | 3854 | 2.56 | 3.21 | 4.12 | 0 |
| hot | gRPC | 3696 | 2.84 | 3.76 | 4.61 | 0 |

Свежесть просмотров под фоновой нагрузкой (по 8 проб на протокол): REST p50 996 мс, max 1016 мс; gRPC p50 1020 мс, max 1048 мс; нарушений порога 2 с нет. Время определяется интервалом flusher (1 с).

Пропускная способность лайков на одном популярном посте (`hot`, около 3.7–3.9 тыс. RPS) ниже, чем на распределённых по постам (около 7 тыс. RPS): строка счётчика сериализует транзакции. Это ожидаемый компромисс решения «лайк и счётчик в одной транзакции» (ТЗ, п. 4.1).

### 3.3 Размер тел сообщений (байты)

Только сериализованные тела, без заголовков, framing и TLS; JSON — protojson, int64 как строки (`go run ./cmd/bench -payload`).

| Операция | JSON запрос | Protobuf запрос | JSON ответ | Protobuf ответ |
|---|---|---|---|---|
| read 20 постов | 104 | 22 | 1235 | 200 |
| views 50 событий | 1685 | 350 | 30 | 2 |
| like | 14 | 2 | 27 | 4 |

Protobuf меньше в 5–6 раз на крупных телах. У реальных GET/PUT/DELETE параметры находятся в URL, поэтому JSON-запрос для них — модель для сравнения.

## 4. Выводы

1. Разница между протоколами в локальном замере небольшая и в обе стороны: gRPC лучше на `views`, `duplicates` и при c=1, REST лучше на `read` при c=10 и 50 и на `likes`/`hot`. Различия сопоставимы с шумом одной машины, особенно в коротком профиле; уверенно утверждать превосходство одного протокола нельзя. Заметное и стабильное преимущество gRPC — размер сообщений.
2. Узкое место — не протокол, а хранилища и ресурсы: деградация при c=50, сериализация на горячем счётчике, память Redis (п. 5).
3. Рекомендация: оставить общий service-слой и оба адаптера; REST для браузера и отладки, gRPC для внутренних клиентов с крупными пачками.
4. Цель 20 000 increments/s из SIS1 в этих измерениях не подтверждена и не заявляется. Достигнуто около 3.0–3.5 тыс. пачек `views` по 50 событий в секунду (то есть примерно 150–175 тыс. событий/с на уровне приёма, из которых новые — все, так как viewer_id уникальны) на одном API с 2 CPU; для лайков 6.6–7.2 тыс. RPS.

## 5. Ограничения и найденная проблема

- **Память Redis при дедупликации.** Первая попытка полного прогона `views` с TTL окна 1 час упала: каждая пачка создаёт до 50 новых ключей дедупликации, за 60 с накапливаются миллионы ключей, Redis исчерпал `maxmemory 256mb` с политикой `noeviction` (ошибки 503, 91 922 на REST), затем контейнер был убит по OOM. Сырые данные сохранены в `benchmarks/results/sis2-oom-failed`. Это подтверждает, что при `noeviction` приём просмотров ограничен памятью Redis: окно дедупликации 3600 с при высоком потоке уникальных пар (post_id, viewer_id) требует много RAM. Для измерений в bench-окружении поставлены `VIEW_TTL=5s` и `maxmemory 768mb` (`benchmarks/compose.yaml`); это отклонение от значения окна по умолчанию (1 час) и оно влияет на результаты `views`. Возможные пути: Bloom/cuckoo-фильтр или хранение дедупликации в Redis Cluster (SIS4).
- Полный профиль выполнен только для `read`. `views`, `likes`, `duplicates`, `hot`, `freshness` — короткий профиль, один прогон. Полный повтор: `python3 benchmarks/run.py --output benchmarks/results/full`.
- Один хост, нет TLS и сети, фоновая нагрузка не исключена, CPU/RAM контейнеров сохранены в `*-resources.json`, но в отчёте не анализируются.
- Нет кэша чтения (упрощение относительно SIS1), нет Redis Cluster, replicas, Kafka, Kubernetes.
- Аутентификация в режиме измерений тестовая (`X-User-ID`); сервис не production-ready с такой схемой.

## 6. Корректность

Интеграционные проверки (`test/integration/counters`, запуск с `-race`, результат в `benchmarks/results/correctness.jsonl`) закрывают пункты 1–11 раздела 9 ТЗ: 100 параллельных лайков, повторное удаление, окно дедупликации без продления, дедупликация между протоколами, конкурентный reconciler, падение worker до и после commit batch, недоступность Redis и PostgreSQL, свежесть ≤ 2 с, deadlines и отмена, ретраи без дублирования эффекта.
